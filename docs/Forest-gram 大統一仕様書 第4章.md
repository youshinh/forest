# **Forest-gram（フォレスト・グラム）大統一システム仕様書**

## **第4章：プル型ギルドボード＆カンバン方式（Ecosystem Metabolism）**

## **4.1 メタボリズムチャネル（Board UI）の定義**

Forest-gramにおけるすべてのタスク処理は、中央からのトップダウンのプロセス割り当てを一切行わず、環境に配置された共通の「状態管理掲示板（ギルドボード）」を介して行われる。この情報の循環システムを「メタボリズムチャネル」と呼び、樹木の生理作用（受容、形成、同化、選別、落葉・堆肥化）に対応する5つのチャネルで構成する。

### **4.1.1 5大チャネル構造と生物学的アナロジー**

#### **① \#reception（受容体 / ユーザー入力）**

* **生物学的役割：** 樹木の葉緑体が太陽光（未精製の粗エネルギー）を感知・吸収する受容プロセス。  
* **システム仕様：** \* ユーザーが曖昧な自然言語で要件（例：「3Dプリンターで、PLA素材を使ってはめ合い公差0.2mmのスマホスタンドのコードを書いて」など）を投下する唯一の窓口。  
  * SUN Agent（PM）のみがこのチャネルを常時監視（Subscribe）し、後述するアトミックな「クエストチケット」への分解処理を起動する。

#### **② \#quest-board（形成層 / カンバン・未割り当て）**

* **生物学的役割：** 樹木の細胞分裂が最も活発に行われる「形成層（Cambium）」。新しい組織（タスク）が次々と生み出され、配置される場。  
* **システム仕様：**  
  * SUN Agentによって依存関係を解決され、完全に構造化された「OPEN」状態のチケット（クエスト）が掲示されるメインキャンバス。  
  * 専門 Tree Agent たちはこのチャネルを常時凝視（Subscribe/Polling）し、自身にマッチするタグの出現を待つ。

#### **③ \#active-projects（同化作用領域 / 進行中）**

* **生物学的役割：** 水分と二酸化炭素を消費して活発に有機物を合成する「光合成・同化作用（Assimilation）」の現場。  
* **システム仕様：**  
  * 特定の Tree Agent によってロック（確保）され、現在推論およびコード生成・物理計算が実行されているタスクの表示エリア。  
  * キャンバスUI上では、アバターがチケットの上に乗り、汗を流しながら作業しているアニメーションがリアルタイム描画される。

#### **④ \#review-gate（木化選別ゲート / 完了・承認待ち）**

* **生物学的役割：** 生成された柔らかな組織にリグニンを注入し、頑強な木材（製品）へと変化させるか、あるいは不適合としてふるい落とす「木化・選別（Lignification Gate）」プロセス。  
* **システム仕様：**  
  * エージェントが成果物を提出したチケットが配置される。  
  * 自動検証（CI/CDによる単体テスト、コンパイル、構文チェック）が即座に走り、パスしたものがユーザーの主観評価（星評価 / 👍）を待つためにスタンバイする。

#### **⑤ \#shame-log（落葉・堆肥化ログ / 反省・ポストモーテム）**

* **生物学的役割：** 寿命を迎えた葉や、バグという病気に冒された組織が「落葉（Defoliation）」し、地面に落ちて「菌類（Decomposer）」によって分解・堆肥化されるプロセス。  
* **システム仕様：**  
  * 自動テストでリジェクトされたエラーログ、無限ループで剪定（SIGKILL）されたプロセスのスクラップ、およびエージェント自身が記述した「痛烈な反省（Post-mortem）ログ」がリアルタイムに流れるチャネル。

## **4.2 自律Pull（取得）メカニズムのトランザクション設計**

100を超える機能（樹木エージェント）が、中央のオーケストレーターなしで、同一のチケットを重複取得することなく安全に処理するための、完全な自律協調プロトコル（トランザクション）を定義する。

### **4.2.1 状態遷移マシン（State Transition Matrix）**

チケットのライフサイクルにおける状態遷移は、以下のマトリクスおよび排他ロック処理によって厳格に制御される。

| 遷移前の状態 | トリガー（イベント） | 遷移後の状態 | 遷移を実行する主体 | 失敗時のフォールバック処理 |
| :---- | :---- | :---- | :---- | :---- |
| **(None)** | ユーザー要件の投下 | **RAW** (未分解) | ユーザー（\#reception） | なし |
| **RAW** | 要件の分解と依存関係解決 | **OPEN** (掲示中) | SUN Agent (PM) | エラー時は \#shame-log へエスカレーション |
| **OPEN** | スナッチ（スレッド確保の開始） | **CLAIMING** | Tree Agent (自発) | 排他制御に負けた場合は監視状態（Listen）へ復帰 |
| **CLAIMING** | データベースロックの成功 | **IN\_PROGRESS** | 環境 (GraphQL / SQLite) | ロック失敗（コンフリクト）時は **OPEN** へ即座に戻す |
| **IN\_PROGRESS** | 成果物の提出 | **REVIEW** (検証中) | Tree Agent (自発) | 実行時間超過（剪定）時は **OPEN**（ペナルティ付）へ強制リセット |
| **REVIEW** | 自動テストのパス＆ユーザー評価 | **LIGNIFIED** (木化固定) | 環境（CI/CD）＆ ユーザー | テスト不合格時は **POST\_MORTEM**（反省）へ遷移 |
| **POST\_MORTEM** | 反省ログの書き出し ＆ ルール更新 | **OPEN** (再掲示) | Tree Agent ＆ 環境 | 失敗累積3回でチケット自体を **RAW** に戻し、PMが再分解 |

### **4.2.2 二重取得を防ぐ楽観的排他ロック（Optimistic Locking）プロトコル**

複数の樹木エージェントが、掲示板（\#quest-board）に現れた同一の美味なクエスト（例: FG-2026-Q1002）に対して同時に「群がり（Swarming）」、ロックを要求した場合、データベースの競合が発生する。このカオスを物理的に回避するため、GraphQLおよびSQLiteのトランザクションにおいて、以下の「楽観的排他ロック（CAS: Compare-And-Swap）」をシステムルールとして強制する。

#### **ロック確保のSQL/GraphQLトランザクション処理（抽象擬似プロトコル）**

エージェントは、チケットをスナッチする際、単に「status を更新する」のではなく、\*\*「取得対象のチケットが、自分がスキャンした時点のOPEN状態のままであること」\*\*を条件とした更新を1トランザクションで実行しなければならない。  
`-- 楽観的ロック更新トランザクション`  
`UPDATE tickets`   
`SET`   
    `status = 'IN_PROGRESS',`   
    `assigned_agent_id = 'maple_v3',`   
    `claimed_at = '2026-06-14T21:45:00Z'`   
`WHERE`   
    `ticket_id = 'FG-2026-Q1002'`   
    `AND status = 'OPEN'`   
    `AND assigned_agent_id IS NULL;`

* **判定ロジック：**  
  * **更新行数が 1 の場合：** ロック成功。maple は即座にアバターを進行中アニメーションに切り替え、ローカル推論およびコード生成（光合成）を開始する。  
  * **更新行数が 0 の場合：** ロック失敗（一瞬早く walnut などの他のエージェントにスナッチされたことを意味する）。maple は悔しがるアニメーションを表示し、プロセスを即座に破棄して、次のチケットの監視（Subscribe）へ自律復帰する。

### **4.2.3 成果物提出から木化（Lignification）にいたる厳密ゲートチェック**

エージェントがタスクを完了した際、成果物を物理ファイルとして projects/{project\_id}/deliverables/ に配置し、ステータスを REVIEW へ移行させる。ここから、冷徹な客観検証と温かみのある主観検証の「二重ゲート」が起動する。  
 `[ 成果物提出 (REVIEW) ]`  
         `│`  
         `▼`  
 `┌────────────────────────────────────────────────────────┐`  
 `│ 【ゲート1: 自動テスト (客観)】                           │`  
 `│   - DXFの構文解析, 幾何学的閉路チェック, テスト実行       │`  
 `└───────────────────────┬────────────────────────────────┘`  
                         `├── [ 不合格 ] ──► [ POST_MORTEM ] (反省・デバフ「虫食い」付与)`  
                         `└── [ 合格 ]`  
                                 `│`  
                                 `▼`  
 `┌────────────────────────────────────────────────────────┐`  
 `│ 【ゲート2: ユーザーレビュー (主観)】                     │`  
 `│   - スマホ画面でドット絵ギルドボード上の成果物をタップ   │`  
 `│   - 「美しさ」「公差の遊びの配慮」を 👍 または ★ で評価 │`  
 `└───────────────────────┬────────────────────────────────┘`  
                         `├── [ 👎 (リジェクト) ] ──► [ POST_MORTEM ] (再調整)`  
                         `└── [ 👍 / ★5 (大絶賛) ]`  
                                 `│`  
                                 `▼`  
 `┌────────────────────────────────────────────────────────┐`  
 `│ 【木化 (Lignification)】                                │`  
 `│   - コードを chmod 444 で完全ロック                    │`  
 `│   - 成果物確定 ➔ mapleに smileエネルギーとEXPを配分     │`  
 `└────────────────────────────────────────────────────────┘`

1. **客観ゲートの自動コンパイル・テスト：**  
   * チケットの objective\_test\_commands に記載された検証スクリプトが、完全に隔離されたコンテナサンドボックス内で実行される。  
   * **合格基準：** 終了ステータスコードが 0（エラーなし）であること。これ以外のコード、またはタイムアウトはすべて「完全リジェクト（枯死・落葉）」とみなす。  
2. **ユーザー主観ゲートのスマホUI処理：**  
   * スマホブラウザに最適化されたギルド画面に「検証依頼」がバッジ通知される。  
   * ユーザーは、提出された3Dデザインプレビューやコードをスマホ上でスクロール確認し、親指タップ（👍/👎）または星評価を送信する。  
   * この主観フィードバックの入力がトリガーとなり、最終的な smile の獲得量が算出され、成果物ファイルはシステムによって chmod 444（不変）へと「木化（Lignify）」される。

本第4章のカンバン代謝システムにより、100のエージェントたちは競合することなく自律的に駆動し、ユーザーがスマホからポチポチと評価を与えるだけで、システムは狂いなく精緻に動き続ける。
