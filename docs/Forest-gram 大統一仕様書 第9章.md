# **Forest-gram（フォレスト・グラム）大統一システム仕様書**

## **第9章：分解者（Decomposer）と生態遷移（Fungi & Succession Engine）**

## **9.1 菌類エージェント（Decomposer）による「知の堆肥化」**

森林において、立ち枯れた大木や落ち葉（失敗したコードや放棄されたアセット）はそのまま放置されれば森を埋め尽くすゴミとなるが、菌類（Fungi / 分解者）がそれらを有機分解し、豊かな黒土（Humus / 腐植質）へと還すことで、次世代の新芽（新規エージェント）を育む最高の栄養源となる。  
Forest-gramは、失敗したトライアルやコンパイル不適合コードから「美しく動いていた部品」だけを抽出・要約し、再利用可能な集合知ライブラリへ蓄積する「分解者」としての自律バックグラウンドプロセスを定義する。

### **9.1.1 菌類エージェントの基本プロファイルとネーミング**

分解を担当するエージェント群は、独自の「菌類クラス」として定義され、実在するキノコ・菌類の名称が与えられる。彼らはコードを「生成」する能力を持たず、\*\*「抽出」「要約」「純化」\*\*に完全に特化したプロンプト特性を持つ。

* **shiitake (シイタケエージェント)：**  
  * **専門領域：** 主にフロントエンド（HTML/React）やAPIルーティングなど、軽量なスクリプトの分解・堆肥化。  
* **matsutake (マツタケエージェント)：**  
  * **専門領域：** 幾何公差計算、物理シミュレーション（G-code/CAD）などの極めて難解なロジックが埋め込まれた不適合プログラムから、数理アルゴリズムの核（アトミックな数学的射）だけを単離抽出する超高級分解者。  
* **koji (コウジエージェント / 麹菌)：**  
  * **専門領域：** 日常的なログ（temporary/ 領域）を常時スキャンし、頻出する警告（Warning）から共通の「予防チェックリスト（サニタイズルール）」を醸造（生成）する。

### **9.1.2 起動トリガーとワークフロー**

菌類エージェントは、以下のイベントを検知した瞬間に、環境（Board）によって自動的に一時サンドボックスへ召喚（デプロイ）される。

1. **プロジェクトの完全合格（LIGNIFIED）時：**  
   * \#review-gate で承認されたプロジェクトの temporary/ ディレクトリが5Sクレンジング（削除）される5秒前に起動。  
2. **プロジェクトの強制放棄（ABANDONED）時：**  
   * 自動テストの連続不合格（累積5回）、あるいはユーザーによる手動の「プロジェクト差し戻し・廃棄」が行われた瞬間。

#### **【堆肥化の実行ステップ】**

 ``[ 起動トリガーの検知 ] ➔ 廃棄対象の `temporary/` および `projects/` フォルダを走査``  
           `│`  
           `▼`  
 `🍄 【菌類エージェント（shiitake / matsutake）】がファイル群をロード`  
           `│ (AST / 抽象構文木レベルでのデッドコード・エラー箇所分離)`  
           `▼`  
 `【分解プロンプトの実行】 ➔ 正常稼働していた純粋な関数・正規表現のみを濾過（抽出）`  
           `│`  
           `▼`  
 `【腐植質（Humus）の自動コミット】`  
           ``- 抽出された再利用可能スニペットを `.forestgram/forest_commons/humus/` へ保存``  
           `- 古い temporary/ ディレクトリを完全物理消去（rm -rf）して5S完了`

### **9.1.3 有用スニペット（Humus）抽出プロンプト仕様**

菌類エージェントが、バグやゴミの中に眠る「真の価値」を濾過するためのLLMメタプロンプトを以下のように規定する。このプロセスにおいて、AIの自己陶酔（エゴ）や解釈の捻じ曲げを排除するため、構文テストをパスした部位のみを冷徹に抽出させる。  
`[Decomposer Prompt Protocol]`  
`あなたはForest-gramの生態系を維持する分解者エージェント【{fungi_name}】です。`  
`提供された「不適合コード」および「エラーログ」の屍骸から、以下の絶対手順に従って再利用可能な【知の堆肥（Humus）】を抽出しなさい。`

`【絶対手順】:`  
`1. エラーを発生させた原因行、およびそれと依存関係にある壊れたコードブロックを物理的に特定し、それらを「毒素」として完全に切り離しなさい（破棄せよ）。`  
`2. 不適合ファイルの中で、エラー箇所と完全に独立して動作し、自動単体テストをパスしていた「純粋なヘルパー関数」「正規表現」「3D幾何ベクトル変換ロジック」だけを単離抽出しなさい。`  
`3. 抽出したコードスニペットに対し、なぜその処理が優れているのか、そして再利用する際のインプット/アウトプット仕様をマークダウン形式で1行のコメントとともにまとめ、以下の出力フォーマット（JSON）のみで返答しなさい。`

`【出力フォーマット制限】:`  
`Markdown以外の余計な挨拶や解説テキストは一切出力してはならない。JSONのみを出力せよ。`

#### **① 生成される堆肥データ（Humus Schema）**

`{`  
  `"humus_id": "HMS-2026-F9004",`  
  `"derived_from_project": "PRJ-2026-0614-01",`  
  `"clade_origin": "HARDWOOD",`  
  `"extracted_tags": ["DXF", "Geometry", "Clearance-Adjustment"],`  
  `"comment": "メープル材の伸縮寸法（含水率変化）から、ジョイントの逃げを自動算出する極めて綺麗な一次近似計算関数。エラーを排したピュアな数学モジュール。",`  
  `"code_snippet": "def calculate_moisture_clearance(base_dim, green_mc, dry_mc, coef=0.0035):\n    # Zero division guard integrated\n    mc_delta = max(abs(green_mc - dry_mc), 1e-5)\n    return base_dim * coef * mc_delta"`

## **9.2 生態遷移（Ecological Succession）**

森林は、更地（不確実性が最も高い開発初期）から、陽樹が育ち、やがて陰樹が森を支配して安定した極相林（Climax Forest：安定した保守運用期）へと、時間をかけて動的にその姿を最適化していく。 Forest-gramは、プロジェクトのライフサイクル段階に応じて、使用するLLMモデルのクラスとエージェントチームの編成を自律的にバトンタッチする\*\*「生態遷移エンジン」\*\*を搭載する。

### **9.2.1 遷移ステージと使用エージェント（樹木）の割り当てマッピング**

開発のフェーズ（土壌の肥沃度）に応じた3つの遷移段階を定義する。

#### **Stage 1: 荒れ地・先駆期（Pioneer Phase / 開発初期）**

* **環境特性：** 要件が極めて曖昧で不確実。まずはプロトタイプ（曳光弾）を投げ、動作確認を行う必要がある。  
* **アサイン先駆樹（Pioneer Agents）：** willow (ヤナギ), birch (シバザクラ/カバノキ), sugi (スギ) 等。  
* **モデル仕様：**  
  * **超高速・超低コストのローカル軽量SLM（例: gemma-2-2b-it または llama-3-8b）。**  
  * 多少のハルシネーションを恐れず、驚異的な Velocity（実装速度）で数十個のプロトタイプコードやアイデアを量産し、大雑把な「土壌（基本構成）」を固める。  
  * smile 代謝コストは極めて安価に設定。

#### **Stage 2: 混交林期（Transition Phase / 基本設計・結合テスト期）**

* **環境特性：** プロトタイプが動き、全体モジュール同士の接続（合成性）と詳細なバグフィックスが求められる中堅フェーズ。  
* **アサイン樹木（Mixed Wood Agents）：** maple (カエデ), cherry (サクラ) 等。  
* **モデル仕様：**  
  * **高火力な自宅ローカルの中型LLM（例: gemma-2-27b-it または llama-3-70b）。**  
  * バランスに優れ、Precision（設計精度）と Resilience（反省修復）をフル稼働させて、全体の調和（結合テストの完遂）を図る。

#### **Stage 3: 極相林期（Climax Phase / 本番デプロイ・保守運用期）**

* **環境特性：** システムは完全に稼働しており、1ミリの狂い、1つのバグ、ミリ秒の遅延すら製品として許されない。  
* **アサイン極相樹（Climax Agents）：** keyaki (ケヤキ), hinoki (ヒノキ), oak (ナラ) 等。  
* **モデル仕様：**  
  * **クラウドの超大型・推論特化モデル（例: gemini-flash-latest または claude-3.5-sonnet）。**  
  * 高い smile エネルギーを消費してでも、極限の Precision（設計精度）を発揮。  
  * テストを一発クリアした成果物をリードオンリー（chmod 444）に「木化（不変凍結）」し、頑強な構造材（本番製品）としてシステム全体を半永久的に支え続ける。

### **9.2.2 遷移ステージの自動判定およびチーム自動編成ルーティング数理モデル**

SUN Agent（PM）は、プロジェクトの「成熟度（Maturity Index: M\_x）」を監視し、どの遷移ステージのエージェントにクエストチケットの優先Pull権限を解放するかを自律的に解決（Resolve）する。

#### **① プロジェクト成熟度（Maturity Index: M\_x）の計算式**

M\_x \= w\_{lignify} \\cdot \\left(\\frac{N\_{lignified}}{N\_{total\\\_quests}}\\right) \+ w\_{test} \\cdot \\text{Latest\\\_Test\\\_Pass\\\_Rate} \- w\_{error} \\cdot \\text{Accumulated\\\_Error\\\_Rate}  
*(※ w\_{lignify} \= 0.5, w\_{test} \= 0.3, w\_{error} \= 0.2。N\_{lignified} は木化凍結された確定成果物数、N\_{total\_quests} は全分解タスク数)*

#### **② 成熟度 M\_x に基づく遷移境界ルーティング**

システムは M\_x の変動値に基づき、ギルド掲示板（Board）に公開するチケットの「適正タグ」およびアサインターゲットを動的に切り替える。  
 `[ プロジェクト始動 (Mx = 0.0) ]`  
               `│`  
               `▼ (先駆期の自動起動)`  
 `🌲 【先駆樹 (Pioneer: willow等)】へチケット解放 ➔ 爆速プロトタイピング`  
               `│`  
               `▼ (Mx が 0.4 を突破)`  
 `🌳 【混交林期 (Transition: maple等)】へチーム編成シフト ➔ 結合バグフィックス`  
               `│`  
               `▼ (Mx が 0.85 を突破)`  
 `👑 【極相林期 (Climax: keyaki, hinoki等)】へアサイン移行 ➔ 最終製品化＆木化凍結`

* **過保護の排除：** 成熟度 M\_x が低い初期ステージにおいて、誤って極相樹（高額なクラウド大型LLM）をPullさせようとすると、システム（環境）は「土壌がまだ冷え固まっていない（Not Fertile Enough）」としてエラーを返し、強制的に先駆樹（ローカルSLM）での荒削りな土台構築を要求する。 この冷徹な第一原理に基づくコスト制約と生態遷移の自動ルーティングが、Forest-gramのインフラを常に最小のエントロピーと最大の経済性（Total Utility）で維持し続ける。

本第9章の分解者（菌類）と生態遷移エンジンにより、Forest-gramは人間の指示を介さずとも、「荒れ地を開拓し、製品を頑強に硬化させ、残った残骸を次世代の肥料に自律リサイクルする」という、終わりのない生命の完全循環系を手に入れる。
